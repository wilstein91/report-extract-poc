# 증권사 리포트 핵심 항목 추출 PoC

투자 판단에 쓰는 재료를 만드는 앞단 작업입니다.
증권사 리포트 PDF에서 투자의견·목표주가·추정치를 표로 옮기는 일을
자동화할 값이 있는지 판단하기 위해 최소한만 만들어 확인합니다.

작성: Sung, Hyun-Joon · 시작 2026-09-22

---

## 1. 후보 지점 세 개

| | A. 리포트 → 숫자 표 추출 | B. 공시 스크리닝 | C. 읽은 자료 검색 |
|---|---|---|---|
| 업무 유형 | 입력과 전사 | 분류와 배분 | 검색 |
| 지금 처리 방식 | PDF 열어 눈으로 읽고 엑셀에 입력 | 공시 제목 훑고 볼 것만 클릭 | 파일명과 Ctrl+F |
| 병목 | 판단이 아니라 손 | 건당 판단은 쉽고 건수가 많음 | 자료에 붙은 설명이 없음 |
| 발생량 | (측정 필요) | 하루 수백 건 | (측정 필요) |
| 틀렸을 때 | 원본과 대조하면 드러남. 되돌릴 수 있음 | 중요 공시를 놓치면 되돌리기 어려움 | 못 찾으면 아쉬운 정도 |
| 채점 자료 | 숫자라서 정답이 객관적 | "봤어야 했다" 기록이 없음 | 정답 문서를 손으로 지정해야 함 |

### 고른 것과 뺀 것

**A를 골랐습니다.** 정답이 숫자라서 채점이 이분법으로 끝나고,
원본 PDF를 공개된 곳에서 받을 수 있어 자료를 오늘 안에 모을 수 있습니다.

**B는 판정 기록이 없어 뺐습니다.** 과거 공시에 대해 "봤어야 했다 / 무시해도 됐다"를
남겨둔 적이 없습니다. 교안 기준으로 이 업무에 지금 필요한 것은 모델이 아니라
판정을 기록으로 남기는 절차입니다.

**C는 자료량이 부족해 뺐습니다.** 정답을 만들 만큼 쌓인 문서가 없습니다.

### 처음부터 대상에서 제외한 것

투자 업무에서 먼저 떠오르는 세 가지는 교안의 "적용하지 않을 업무"에 해당해 제외했습니다.

| 제외한 것 | 이유 |
|---|---|
| 주가 예측 · 매매 신호 생성 | 틀렸을 때 되돌릴 수 없음. 손실이 그대로 발생 |
| "좋은 종목" 판별 | 판정 기준이 사람마다 다름. 좋은 종목의 정의를 문장으로 쓸 수 없음 |
| 백테스트로 전략 채점 | AI 문제가 아니라 결정론적 계산. 그리고 미래 참조 편향과 과최적화로 채점 자체가 신뢰할 수 없게 됨 |

AI가 들어갈 자리는 최종 판정이 아니라 재료를 만드는 앞단으로 한정했습니다.
매수 판단은 사람이 합니다.

## 2. 성공 기준

만들기 전에 적었습니다.

```
① 리포트 10건 × 7항목 = 70개 중 오류 3개 이하
② 모든 값에 원본 위치(페이지·줄)가 붙어, 틀린 값을 원본에서 찾을 수 있다
③ 읽지 못한 항목은 빈칸으로 두고 그럴듯한 값을 지어내지 않는다
```

**뽑을 항목 일곱 개**
종목명 / 증권사 / 작성일 / 투자의견 / 목표주가 / 현재주가 / 당해연도 영업이익 추정치

**숫자의 근거**
정답표를 손으로 채우면서 건당 소요 시간을 함께 기록합니다(`data/truth/ground_truth.csv`의 `기입소요초`).
이 값이 현행 수준이자 기준선의 속도가 됩니다. (측정 전 — 채우고 나서 이 자리에 기록)

**③번이 이 PoC의 어려운 부분입니다.**
언어 모델은 빈칸을 두라고 지시하지 않으면 형식에 맞는 그럴듯한 값을 채웁니다.
그 경우 오류 메시지도 없고 결과도 비어 있지 않아 검산 없이 넘어가게 됩니다.
그래서 ②번(원본 위치)과 ③번(빈칸 허용)을 성공 기준에 같이 넣었습니다.

## 3. 후보 구성

증권사 리포트는 스캔본이 아니라 디지털로 생성된 PDF라 텍스트 레이어가 있습니다.
따라서 이 PoC의 문제는 글자를 읽는 것(OCR)이 아니라,
추출된 텍스트에서 **어느 숫자가 어느 항목인지 고르는 것**입니다.

한 리포트 안에 목표주가 · 직전 목표주가 · 현재주가가 나란히 있고, 형식이 같습니다.

| | ① 기준선 | ② 로컬 모델 | ③ 외부 API |
|---|---|---|---|
| 실행 위치 | 로컬 | 노트북 | 외부 |
| 방식 | PyMuPDF 텍스트 + 정규식 규칙 | 텍스트 → 로컬 언어모델 | 텍스트 → API 언어모델 + 구조화 출력 |
| 만들어진 목적 | 이 일 전용 규칙 | 범용 | 범용 |
| 결과의 형태 | 위치를 정확히 앎 | (확인 필요) | (확인 필요) |
| 자료가 나가는가 | 안 나감 | 안 나감 | **나감** |
| 비용 | 없음 | 없음 | 호출당 과금 |

①이 이미 쓰는 방식에 해당하는 기준선입니다.
자료가 밖으로 나가면 안 되는 조건이 확정되면 ③은 점수와 무관하게 제외합니다.
(→ 결론은 `docs/sources.md` 라이선스 표와 함께 기록)

## 4. 측정 결과

10건 × 7항목 = 70칸. 채점 규칙은 `src/report_extract_poc/schema.py` 에 있고 돌리기 전에 정했다.

| 후보 | 맞음 | 틀림 | ① 오류 3개 이하 | ② 근거 위치 | ③ 빈칸 | 건당 초 |
|---|---:|---:|:---:|---:|:---:|---:|
| ① 규칙 (PyMuPDF+정규식) | **50/70** | 20 | ❌ | 42/52 | 3/4 | **0.00** |
| ② gemma4:e4b (로컬) | 46/70 | 24 | ❌ | **56/60** | 3/4 | 89.05 |
| ~~qwen3.5:0.8b~~ (공부용) | 45/70 | 25 | ❌ | 12/67 | 2/4 | 22.35 |
| ⓪ 목록 스크래핑 | 16/70 | 54 | ❌ | 0/18 | 2/4 | **0.00** |
| ③ Claude | — | — | — | — | — | **미측정 (API 키 없음)** |

**세 기준 모두 통과한 후보가 없다.** 그러나 전체 점수보다 항목별이 중요하다.

### 항목별 정답 수

| 항목 | ① 규칙 | ② gemma4 | ⓪ 목록 | 읽어야 하는 것 |
|---|---:|---:|---:|---|
| 목표주가 | **10/10** | 8/10 | **10/10** | 라벨 옆 값 |
| 증권사 | **10/10** | 3/10 | 0/10 | 문서 어딘가의 고유명사 |
| 작성일 | 9/10 | **10/10** | 0/10 | 라벨 옆 값 |
| 현재주가 | 9/10 | 9/10 | 0/10 | 라벨 옆 값 |
| 종목명 | 6/10 | **9/10** | 0/10 | 종목코드 옆 이름 |
| 투자의견 | 6/10 | 5/10 | 6/10 | 라벨 옆 값 + 표기 흔들림 |
| **영업이익추정치_당해** | **0/10** | **2/10** | **0/10** | **실적 표의 열을 짚어야 함** |

라벨 옆 값을 읽는 여섯 항목은 규칙으로 충분하다. 언어 모델을 붙일 이유가 없다.
갈리는 것은 표의 열을 짚어야 하는 한 항목이고, **거기서 전 후보가 무너졌다.**

### 가장 중요한 발견 — 근거는 진짜인데 값이 틀린다

gemma4 는 값마다 근거가 된 원문 조각을 함께 냈고, 코드가 그 조각이 실제 원문에
있는지 대조했다. 통과율 **56/60**. 즉 거의 지어내지 않았다.

그런데 영업이익 추정치는 8건이 틀렸다. 틀린 방식이 이렇다.

| file_id | 정답 | 모델이 낸 값 | 무엇을 가져왔나 |
|---|---:|---:|---|
| 01 | 1047 | 1,420억원 | **3분기** 영업이익 (정답은 연간) |
| 03 | 71 | 710 | 자릿수가 다른 값 |
| 04 | 85 | 1,597 | 다른 행의 값 |
| 05 | 429 | 3,655억원 | 영업이익이 아닌 값 |
| 06 | 824 | 32,194 | 영업이익이 아닌 값 |
| 10 | 0.4 | 3억원 | 다른 값 |

**전부 그럴듯한 숫자다. 오류 메시지도 없고 빈칸도 아니고 근거도 원문에 실재한다.**
모델은 거짓말을 하지 않았다. 원문에 있는 진짜 숫자를 엉뚱한 자리에서 가져왔을 뿐이다.

여기서 배운 것:

> 근거 대조는 **지어냈는지**는 잡지만 **엉뚱한 자리에서 가져왔는지**는 잡지 못한다.

교안의 "값이 계산된다는 것은 그 값이 의도한 것을 재고 있다는 뜻이 아니다" 가
이 형태로 나타났다. 그리고 입력·전사 유형이 "틀렸을 때 알아채기 가장 어렵다"는
지적도 그대로 확인됐다. 정답표를 미리 만들어 두지 않았다면 전부 맞은 줄 알았을 것이다.

### 성공 기준 판정

| 기준 | 결과 |
|---|---|
| ① 70개 중 오류 3개 이하 | ❌ 전 후보 미달 (최소 20개) |
| ② 모든 값에 원본 위치 | 규칙 42/52, gemma4 56/60, qwen 12/67 — **소형 모델은 근거를 내지 못해 검산이 불가능** |
| ③ 없는 것은 빈칸 | 09번(표기 자체가 없음)은 전 후보 통과. 10번은 아래 결함 참조 |

### 설계 결함 두 개 — 결과를 보고 고치지 않고 기록만 한다

**결함 1. "없음"의 정의를 섞었다.**
성공 기준 ③ 을 쓸 때 두 가지를 구분하지 않았다.

- (a) 리포트에 그 항목 자리가 **아예 없다** → 09번
- (b) 리포트에 **"없음"이라고 적혀 있다** → 10번 투자의견 `Not Rated`

10번 원문에는 `Not Rated` 가 실제로 인쇄돼 있다. 모델이 그 값을 낸 것은
원문을 정확히 옮긴 것인데, 정답표가 빈칸이어서 "지어냄"으로 잡혔다.
정답 정의가 틀린 것이지 모델이 틀린 것이 아니다.

정답을 결과 뒤에 고치면 채점이 성립하지 않으므로 위 표는 그대로 둔다.
정의를 고쳤을 때의 값은 이렇다. **순위는 바뀌지 않는다.**

| 후보 | 원 채점 | 10번 투자의견 정답을 `Not Rated` 로 고치면 |
|---|---:|---:|
| ① 규칙 | 50/70 | 51/70 |
| ② gemma4 | 46/70 | 47/70 |
| qwen3.5:0.8b | 45/70 | 45/70 (`Buy` 라고 답해 여전히 오답) |
| ⓪ 목록 | 16/70 | 17/70 |

**결함 2. 증권사 항목의 비교 조건이 달랐다.**
규칙 후보는 증권사를 찾을 때 문서 전체를 보게 했고, 언어 모델에는 첫 페이지만 주었다.
증권사명은 첫 페이지에 없는 경우가 많아 규칙 10/10, gemma4 3/10 이 나왔다.
**이 격차는 모델 성능 차이가 아니라 내가 준 입력의 차이다.** 같은 조건으로 다시 재야 한다.

## 5. 판단

**기준 미달. 다만 미달 이유가 모델 성능이 아니다.**

**1. 항목 여섯 개는 AI 없이 끝난다.** 목표주가·현재주가·작성일·종목명은 규칙으로 충분하고,
목표주가는 규칙과 목록 스크래핑이 모두 10/10 이었다. 여기에 언어 모델을 붙이면
건당 89초와 9.6GB 메모리를 쓰고 정확도는 오히려 떨어진다.

**2. 남는 항목은 하나인데, 거기서 전부 실패했다.** 실적 표의 열을 짚는 일은
규칙 0/10, 로컬 모델 2/10 이다. 그리고 실패가 **조용하다.** 값이 나오고 근거도 붙는다.
사람이 전량 검산해야 하는데, 그러면 자동화의 이득이 사라진다.

**3. 기준선이 이겼다.** 종합 1위는 AI 를 쓰지 않는 규칙 후보다(50/70, 0.00초).
교안이 말한 "이 업무에는 지금 방식이 낫다" 에 해당한다.

**4. 속도 숫자에는 조건이 붙는다.** gemma4 의 89초는 Intel Arc 내장 그래픽 기준이다.
전용 그래픽카드에서는 달라진다. 속도만으로 이 모델을 떨어뜨리면 안 된다.

**5. 적용 지점 자체가 업무와 어긋나 있었다.** PoC 를 진행하며 드러난 것이 있다.
처음에 병목을 "PDF 에서 숫자를 옮겨 적는 손"으로 잡았으나,
실제 병목은 **하루 8~50건 중 무엇을 볼지 고르는 일**이었다.
표를 자동으로 만들어 주어도 읽고 판단하는 시간은 줄지 않는다.

또한 추출 항목 일곱 개도 실제 업무를 담지 못했다. 실무에서는 더 많은 값을 보고
내용을 추리기까지 하는데, 이번에 고른 항목은 "라벨 옆 값 읽기"에 치우쳐 있었다.
교안이 "쉬운 것만 모으면 표가 아무것도 알려 주지 않는다" 고 경고한 그 상태에
자료가 아니라 **항목 선정**에서 빠졌다.

### 그래서 지금 쓸 수 있는 것

⓪ 목록 스크래핑은 AI 없이 0 초에 돌고 목표주가 10/10 이다.
매일 아침 전체 리포트 목록을 표로 받는 용도로는 **오늘 코드로 이미 쓸 수 있다.**
값을 읽고 판단하는 일은 사람이 한다.

## 6. 회고

**1. 후보 셋 중 고른 것과 뺀 것의 차이는?**

고른 A(리포트 → 숫자 표)는 정답이 숫자라서 채점이 이분법으로 끝나고,
공개된 곳에서 자료를 당일에 모을 수 있었다.
B(공시 스크리닝)는 "봤어야 했다/무시해도 됐다"는 판정 기록이 없어 뺐다.
교안 기준으로 그 업무에 지금 필요한 것은 모델이 아니라 판정을 기록하는 절차다.
C(읽은 자료 검색)는 정답을 만들 만큼 문서가 쌓여 있지 않아 뺐다.

역설적으로 **A 를 고른 근거였던 "채점이 쉽다"가 함정이었다.**
채점이 쉬운 항목은 규칙으로도 풀리는 항목이었다.

**2. 성공 기준의 숫자를 어디서 가져왔는가? 현행 수준을 실제로 재 보았는가?**

재 보았다. 정답표를 손으로 채우면서 건당 소요 시간을 함께 기록했다
(`data/truth/ground_truth.csv` 의 `기입소요초`).

```
건당 평균 23.6초 · 10건 총 3.9분 · 최소 12초 최대 32초
```

이 숫자가 결론을 바꿨다. gemma4 의 89초는 **사람보다 3.8배 느리다.**
현행 수준을 재지 않았다면 "89초면 빠르다"고 썼을 것이다.

다만 이 측정에는 한계가 있다. 정답을 만든 사람이 곧 현행 수준을 잰 사람이므로
**사람의 오류율은 측정되지 않았다.** 사람이 틀린 자리는 정답이 되어 버린다.

**3. 실행 위치나 라이선스 때문에 제외한 후보가 있는가? 점수로는 몇 위였는가?**

있었고, 그 제외를 되돌렸다.

처음에는 한경컨센서스의 재배포 고지("전재, 복사 또는 대여 될 수 없습니다")를 근거로
외부 API 후보를 제외했다. 그러나 **제외 조건을 정하는 것은 업무를 아는 사람이지 도구가 아니다.**
실제 도입 시 Claude 를 쓸 계획임이 확인되어 후보로 되돌렸고, API 키가 없어 측정하지 못했다.
점수를 추측으로 채우지 않았으므로 순위는 알 수 없다.

라이선스에서 예상 밖의 것이 하나 나왔다. **AI 가 아닌 후보가 더 엄격했다.**

| | 라이선스 | 배포 시 |
|---|---|---|
| gemma4:e4b (AI) | Apache-2.0 | 제한 없음 |
| PyMuPDF (AI 아님) | AGPL-3.0 / Artifex 상용 별매 | **소스 공개 의무 또는 유료 라이선스** |

"AI 를 안 쓰면 라이선스가 안전하다"는 생각이 틀렸다는 사례다.
확인은 저장소 표시가 아니라 설치된 배포본의 메타데이터에서 했다(`docs/sources.md`).

**4. 기준을 넘지 못한 항목은 다음에 무엇을 바꿔 다시 확인하겠는가?**

| 바꿀 것 | 이유 |
|---|---|
| 후보 ③ Claude 를 같은 10건·같은 정답표로 측정 | 실제 도입할 후보인데 이번에 재지 못했다 |
| 증권사 항목을 같은 입력 조건으로 재측정 | 규칙에만 전체 문서를 주었다 (결함 2) |
| "없음"의 정의를 (a)자리 없음 / (b)없다고 적힘 으로 나눈다 | 결함 1 |
| 영업이익 항목에 **표 구조**를 넘긴다 | 지금은 평문 텍스트만 주어 열 위치가 사라진다. 이 항목의 실패는 모델이 아니라 입력 형식 탓일 수 있다 |
| 항목을 실제 업무에 맞게 다시 고른다 | 라벨 옆 값 읽기에 치우쳤다 |
| 목록 자동 수집을 2주 돌려 "놓쳐서 아쉬웠던 리포트"를 기록한다 | 진짜 병목(무엇을 볼지 고르기)에는 채점 자료가 없다. PoC 보다 기록 절차가 먼저다 |

마지막 항목이 다음 PoC 의 전제 조건이다.
그리고 "내용 추리기"를 다루려면 요약을 채점 가능한 형태로 바꿔야 한다.
`3줄 요약` 은 사람마다 달라 채점할 수 없고, `추정치를 올렸나 내렸나`,
`목표주가 변동 폭 몇 %`, `근거 3개 뽑기` 처럼 구조를 지정하면 채점할 수 있다.
이번에 만든 근거 대조 장치가 그대로 쓰인다.

## 저장소 구조

```
data/reports/          원본 PDF 10건 (재배포 조건으로 커밋하지 않음)
data/truth/            정답표 — 모델을 돌리기 전에 사람이 손으로 작성
data/baseline/         한경 목록에서 받은 값 (후보 ⓪ 의 입력)
src/report_extract_poc/
  schema.py            항목 정의와 채점 규칙 (돌리기 전에 확정)
  pdftext.py           PDF → 텍스트
  listing.py           후보 ⓪
  rules.py             후보 ①
  llm.py               후보 ② (Ollama, 로컬)
scripts/
  make_truth_xlsx.py   정답표 작성용 엑셀 생성
  xlsx_to_csv.py       작성한 엑셀 → CSV
  run.py               후보 하나를 10건에 실행
  score.py             정답표와 대조해 채점
results/runs/          실행마다 새 폴더. 덮어쓰지 않는다
  <시각>_<후보>/output.csv     값 + 근거 위치 + 신뢰도(반올림 없음)
  <시각>_<후보>/evidence.md    사람이 눈으로 보는 근거 대조표
  <시각>_<후보>/meta.json      쓴 인자 전부
results/score.md       채점표
docs/sources.md        자료 출처, 라이선스, 확인 날짜, 실행 환경
```

## 다시 돌려보는 방법

```bash
uv sync
uv run python scripts/run.py --candidate list
uv run python scripts/run.py --candidate rules --window 60 --pages 1
uv run python scripts/run.py --candidate llm --model gemma4:e4b   # Ollama 필요
uv run python scripts/score.py
```

원본 PDF 는 저장소에 없다. `docs/sources.md` 의 `report_idx` 로 다시 받을 수 있다.
판정에 쓰는 값은 코드에 박혀 있지 않고 전부 인자다.
결과는 `results/runs/` 아래 새 폴더로 쌓이며 이전 실행을 덮어쓰지 않는다.
